## 二、Q1：这不是契约级语义，DSH 侧零假设

**证据（可复现）**：

```
$ grep -n 'stream_enabled\|streamEnabled\|静音\|\bmute\b' \
      dsh-astrbot-relay/lib/*.js dsh-astrbot-relay/cordis.patch.yml
（无输出）
```

DSH 侧**完全没有**这个概念。它只按契约 §4 往下发 `text/delta`、`tool/call`、
`reasoning/delta` 等帧，**不关心 IM 侧渲不渲染、渲染多少**。所以：

* 保持 `bridgeVersion` 不变 ✓（若为这个改版本号，反而是在用一个协议版本号记录一件
  与协议无关的事——v6→v7 的增量是图片输入，那才是协议级）。
* **但建议补一句契约说明**（无版本影响，属澄清而非变更）：
  「`text/delta` 是**建议性**的：消费端可以任意合并、节流或整体丢弃而不产生协议后果；
  只有 `message/final` 是权威文本。」——这句话把你们这次的定调**与既有的
  `pending` 回退机制一起**写进了契约，将来别人再问同样的问题就有据可依。

## 三、Q2：工具提示建议**保留**，不要跟着流式一起关

我理解「`· 调用工具 X` 同属刷屏」的直觉，但它和分片不是一个量级的东西：

| | 体量 | 关掉后的后果 |
|---|---|---|
| `text/delta` 分片 | 一次 turn 几十~几百条 | 用户要的就是这个别再刷 |
| `tool/call` 提示 | **每个工具调用一条** | 长 turn 期间**唯一的存活证据** |

关键在**失败模式会重演，只是延迟**：你们改这次语义，是因为「用户关了流式，
`/dsh 问答` 变成哑巴，而他要的只是别再刷屏」。同样的场景在**长 turn** 上完全一样——
关了流式之后问一个要跑 5 个工具、耗时三分钟的问题，用户会**全程看不到任何东西**，
然后得出与当初完全相同的结论：坏了。

**建议**（二选一，我倾向前者）：

1. 拆出独立开关（如 `tool_notice_enabled`，默认跟随 `stream_enabled` 的旧行为），
   想全静的人仍有办法；或
2. 保留当前「一起关」的口径，但至少让**第一次**工具提示必发（或改发一句
   「正在处理…」），别让长 turn 全程静默。

若要压体量，`throttle_ms` 是现成的旋钮——**不要**用「整类关掉」来控频。

## 四、Q3：可以照样算，但别让配置键静默无效

`throttle` 在关流式时照旧计算、却不影响收敛回帖，是**无害开销**，不值得为它加分支。

但请在配置说明里点明它只在开流式时有意义。理由是这个仓库反复在消灭同一类东西：
**「配置键在一条路径上说了谎」**（`reply_render_mode` 只在 agent 回复上生效、
`forwardReasoning` 与本插件配对时没有可见效果——见 §5.1）。一个在某个模式下静默无效的
键，就是同一类问题的下一个候选，而改一句话的成本远低于将来一次排查。

## 五、⚠️ 最重要的发现：**现有测试钉不住这次修复**（已实测）

请求里问「有无遗漏的读点」。读点没漏（见 §6），但**测试漏了一个要害**：

> 你们现有的用例**全部在 turn 开始前**设好 `stream_enabled`。这样的用例，
> 对「turn 开头捕获一次」的旧写法**同样会绿**——也就是说，这次修复的
> **核心卖点（中途改配置立刻生效）根本没有被任何一条用例守住**。

**实测**（把两处现读改回「turn 开头快照」，其余不动）：

| 跑的对象 | 结果 |
|---|---|
| 真码 + 你们原有 59 项 | 59 通过 / 0 失败 |
| **快照版 + 你们原有 59 项** | **59 通过 / 0 失败** ← 套件对这次回归是盲的 |
| 真码 + 我补的 2 条 | **61 通过 / 0 失败** |
| **快照版 + 我补的 2 条** | **59 通过 / 2 失败** ← 恰好只有这两条红 |

我已经把这两条加进 `scripts/test-im-commands.py` 的 §11（紧跟对照组之后），
并把「钩子挂错一格」的坑写进了注释——那是我第一版踩的：
`_touch_frame` 是在**每帧分发之前**调的，所以在第 2 次翻转等于「turn 一开始就开着」，
测不到中途生效。

**它们为什么有敏感性**（而不是又一条空断言）：

* 正向（开→关）：钩在 `event.send` 上，**第一片真的发出去之后**才关。
  真码下第二片被拦住；快照版下第二片照发。
* 反向（关→开）：关着时没有 `event.send` 可挂钩，改钩在每帧都会调的 `_touch_frame` 上
  （第 #3 次 = delta2 处理前）。真码下攒着的分片被补发；快照版下一片都没有。

## 六、读点清点：**没有遗漏**，而且有两处做得对

`_consume_turn` 里往外发的出口一共这些，逐条核过：

| 行（HEAD） | 出口 | 受 `stream_enabled` 管？ | 判断 |
|---|---|---|---|
| 1322 | 等待桥接端回复超时 | 否 | ✓ 异常路径，必须发 |
| 1332–1333 | 事件流中断 | 否 | ✓ 同上（且仅当什么都没发过时） |
| **1346–1349** | **gap 帧「链路抖动，中间有内容丢失」** | **否** | ✓ **正确**，见下 |
| 1359–1371 | `text/delta` 分片 | **是**（且 `due()` 节流） | ✓ 本次改动核心 |
| 1373–1374 | `reasoning/delta` | 否（**永远丢弃**） | ✓ 正确，但见 §5.1 |
| 1376–1380 | `tool/call` 提示 | 是 | 见 §3 |
| 1407–1416 | `turn/end` 的 `reason=error` | 否 | ✓ 正确 |
| 1429–1439 | 收敛回帖（最终回答） | 否 | ✓ 本次改动核心 |

**gap 提示不受开关管是对的**，而且理由比「它是告警」更具体：
`message/final` 到达时它是噪音（最终回答是完整的），但 `message/final` **没到达**时，
`tail = pending`（1431–1432）会把攒下的内容当兜底发出去——**那份内容真的缺了中段**，
此时这条告警是唯一说明。两种情形共用一个出口，保守一点正确。

**顺带表扬一处**：`else: tail = pending`（1431–1432）这个回退，是这次语义变更能安全落地的
关键。没有它，「关流式 + 流中断」就会把已经攒下的内容整段丢掉——那才是真事故。
你们的代码注释（1418–1427）也已经把「四类照发」写全了，配置说明
（`_conf_schema.json` 的 `stream_enabled.hint`）同样写全了：
「最终回答、审批请求、用户问答、链路告警照发」✓。**口径是一致的。**

## 七、其余观察（都不是本次改动的缺陷）

### 7.1 `forwardReasoning=true` 与本插件配对时**没有可见效果**

* DSH 侧：`if (!config.forwardReasoning) return`（`dsh-astrbot-relay/lib/index.js:761`）
  —— 它管的是**发不发**这类帧，默认关。
* IM 侧：`reasoning/delta` → `continue  # 思考过程不进 IM`（`main.py:1373-1374`）
  —— **无条件丢弃**。

于是有人为了让思考过程出现在 IM 里去开它，结果什么都不会发生，从而怀疑桥坏了。
建议在**契约 §4 那张表的 `reasoning/delta` 行**（`docs/BRIDGE-CONTRACT.md:266`）
补半句：「IM 侧当前无条件丢弃该类帧，本键只在对接其它消费端时才有可见效果。」
DSH 侧那个键（`lib/index.js:217`）也**没有任何注释**，一并补上更好。

### 7.2 「哪些键热生效、哪些要重载插件」值得写成一张表

* `_cfg()` 每次现读 `self.config`（`main.py:1060-1065`）→ **热生效**（本次改动依赖这一点 ✓）
* `_transport_or_create()` 把配置**快照**进 transport（`main.py:1067-1070`）
  → token / `bridge_url` 这类**改完要重载插件**才生效

这不是缺陷（重连语义本来就该是显式的），但两者寿命不同却没有任何文档说明。
建议在插件 README 里加一张两三行的表，省下将来「我改了 token 怎么不生效」的排查。

请求 §7 让我留意旧表述。全库搜 `静音` / `mute`，剩下的**每一处都属于
